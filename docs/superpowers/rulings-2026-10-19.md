## 2026-10-22-parts-and-write-per-version

- Ruling: converting non-empty N.PREFIX/N.SUFFIX in old notes to name-prefix/name-suffix is intended — the spec's "Convert and old notes" says so — cost if wrong: none.
- Ruling: the spec's convert test (`GENDER: M` -> gender, `N.PREFIX: Dr` -> name-prefix) had no task; added to Task 2 — cost if wrong: none.
- Ruling: a migrated default row keeps its own reader mark (sinceReader 3), not its sibling's (the spec said copy; the sibling has none) — spec fixed — cost if wrong: none.
- Ruling: accept the multi-device gap: a phone deletes a part before a desktop with a reader-2 base syncs -> that desktop pushes the part back once — same trade-off as labelled dates — cost if wrong: the owner deletes the part again once.
- Ruling: Radicale stores fields it does not know as made of parts (GENDER, X-GENDER) with the `;` escaped. A value with no unescaped `;` but an escaped one is read with the escaped `;` separating the parts, for every field outside the vCard format's ADR/N/ORG (those always split on unescaped `;` only, so `ORG:Smith\; Jones` stays one company) — cost if wrong: a gender identity containing `;` comes back cut at the `;` on such a server; a server that flattened ORG/N/ADR would lose parts (none seen; Radicale keeps them).
- Ruling: rows that write the same field must have the same vCard 3.0 write key (validation error naming both), and fixed rows (uid, name, photo) show their 3.0 key read-only — otherwise a 3.0 card gets two lines for one field or no UID — cost if wrong: setting a 3.0 key for gender takes two edits.
- Ruling (revises the multi-device gap above, after the owner asked why Sync does not just look at the server): a row an older base was read without counts in that base when the note already holds the base's own value (filled on another desktop). A phone removal is then pulled into the note, not pushed back. Applies to labelled dates too. A note that is empty or differs for that row keeps the old reading (server addition, or a conflict) — cost if wrong: a value cleared in Obsidian comes back into the note once when the first Sync after it runs on a desktop that has not synced that contact since the update.
